Response:
**Your understanding is mostly correct.** The key distinction is that **truncation controls how long a return looks ahead, while dynamic exploration controls how long you collect data to obtain coverage.** They address different problems.

### 1. On-policy Monte Carlo (OMC)

Monte Carlo evaluates a policy using discounted costs observed along trajectories generated under that policy. A single observed return tells you **how costly that particular trajectory was**; averaging returns estimates the policy’s **expected** cost.

For a state–action value, you start with the specified state and action, then follow the current policy afterward.

One terminology point: in your assignment, “on-policy” means following the policy being evaluated; “online” means collecting transitions sequentially through actual interaction. These are different properties.

### 2. Truncated on-policy Monte Carlo (TOMC)

Yes—TOMC limits the future costs included in each return to a finite horizon:

$$
\widehat Q(s_\tau,a_\tau)
=
\sum_{k=0}^{T-1}\gamma^k c_{\tau+k}.
$$

In your continuing GridWorld, trajectories need not terminate, so truncation gives a finite waiting time for each return. The tradeoff is **truncation bias**: costs beyond the horizon are omitted.

However, **truncation alone does not solve poor state–action coverage**. A short return is easier to finish, but you still need to reach its starting state–action pair.

### 3. TOMC with dynamic exploration time

**Your description is correct if that is the stopping rule specified in your assignment.** With the policy held fixed, you:

1. Identify required pairs using the policy-probability threshold.
2. Collect an online trajectory until the required pairs have the prescribed number of visits.
3. Collect enough subsequent observations to complete the truncated returns associated with those visits.

Two qualifications matter:

- **A sufficiently likely action is not necessarily a frequently visited pair.** Its state may be hard to reach. Dynamic exploration adapts the collection time; it does not guarantee fast coverage—or even eventual coverage of unreachable states.
- **“Visited once” versus “visited enough times,” and how excluded pairs receive Q-estimates, must follow the assignment’s definition.** Those details affect the estimates passed to SPMD.

Also, “exploration” here need not mean changing the policy to force visits. It can mean **waiting under the current policy until the coverage condition holds**.

So your conceptual picture is sound: **TOMC bounds the return horizon; dynamic exploration adapts the data-collection duration to coverage.**

### TD(0): update from one transition

TD(0) combines the immediate observed cost with an existing estimate of the remaining discounted cost. This is called **bootstrapping**.

Since your SPMD needs state–action values, an on-policy TD update can use:

$$
\delta_t
=
c_t+\gamma\widehat Q(s_{t+1},a_{t+1})
-\widehat Q(s_t,a_t),
\qquad
a_{t+1}\sim\pi(\cdot\mid s_{t+1}),
$$

$$
\widehat Q(s_t,a_t)
\leftarrow
\widehat Q(s_t,a_t)+\alpha_t\delta_t.
$$

This is the SARSA-style TD target, used here to evaluate a **fixed policy**. At a terminal transition in Blackjack, the future-value term is zero.

Your statement that it adjusts the prediction associated with the current visit is exactly right **for tabular TD(0)**. With shared function-approximation parameters, one update can also change predictions elsewhere.

### TD(λ): give earlier visits credit too

Yes—TD(λ) uses **eligibility traces** to retain a decaying record of earlier visits. The current TD error updates not only the current pair but also earlier pairs with nonzero traces.

- **λ = 0:** reduces to TD(0).
- **Larger λ, up to 1:** earlier visits retain more influence, so the current error propagates farther backward.
- Trace decay depends on **both the discount factor and λ**, through their product.

Unlike TOMC, the usual backward-view TD(λ) implementation still updates incrementally; it does not wait to assemble a long sampled return. Reset the traces at Blackjack episode boundaries.

**Larger λ is not automatically better.** It puts more weight on longer-term sampled information and generally trades less reliance on bootstrapping for greater variability. The connection to full Monte Carlo at λ = 1 is clearest in episodic settings with appropriate terminal handling; exact equivalence depends on the update formulation.

For your project, a clear description is: **“We use TOMC as the baseline policy evaluator and compare it with TD(0) and TD(λ), while retaining SPMD for policy optimization.”**

Response:
**They likely mean implementing your policy evaluator in two ways: storing a separate Q-value for every state–action pair (*tabular*), and representing Q-values using features and learned weights (*linear function approximation*).** These describe how you represent the estimates—not different environments or policy-optimization methods.

## 1. Tabular: one estimate per state–action pair

You store a Q-table:

$$
\widehat Q\in\mathbb R^{|\mathcal S|\times|\mathcal A|}.
$$

For your GridWorld, that is **8 states × 4 actions = 32 entries**.

In tabular TD(0), a transition updates only the entry for the current state–action pair:

$$
\widehat Q(s_t,a_t)
\leftarrow
\widehat Q(s_t,a_t)+\alpha_t\delta_t.
$$

Each entry is an independent parameter. Learning about “right from state 0” does not directly change the estimate for “right from state 4.”

Tabular TD(λ) instead maintains a **trace table of the same size**, allowing the current TD error to update earlier visited pairs too.

## 2. Linear: features and a weight vector

Instead of learning every Q-value independently, you choose a feature vector for each pair and learn shared weights:

$$
\widehat Q_\theta(s,a)=\phi(s,a)^\top\theta.
$$

Here:

- **Features** describe the state–action pair and are usually fixed.
- **Weights** are the parameters learned by TD.
- The number of weights equals the number of features.

For GridWorld, possible features could describe position, whether the state is a hazard or goal, and the action. **The feature choice determines what distinctions the evaluator can learn.** For example, action information is necessary to represent different Q-values for different actions at the same state.

For linear on-policy TD(0), the update becomes:

$$
\delta_t
=
c_t+\gamma\phi(s_{t+1},a_{t+1})^\top\theta_t
-\phi(s_t,a_t)^\top\theta_t,
$$

$$
\theta_{t+1}
=
\theta_t+\alpha_t\delta_t\phi(s_t,a_t).
$$

Because weights are shared, **one transition can change predictions for other pairs with overlapping features**.

For linear TD(λ), the trace is a **feature-sized vector**:

$$
e_t=\gamma\lambda e_{t-1}+\phi(s_t,a_t),
\qquad
\theta_{t+1}=\theta_t+\alpha_t\delta_t e_t.
$$

These are accumulating traces; for episodic Blackjack, clear them between hands and use zero future value at termination.

## How this fits your project

| Component | Tabular version | Linear version |
|---|---|---|
| Learned evaluator parameters | Q-table | Weight vector |
| TD(0) update | Current table entry | Weights associated with current features |
| TD(λ) memory | State–action trace table | Feature trace vector |
| Input supplied to SPMD | Learned Q-table | Q-values computed from features and weights |
| Main tradeoff | No representation restriction | Can share information and use fewer parameters, but may introduce approximation error |

**Your SPMD policy can remain tabular in both versions.** For the linear evaluator, compute its predicted Q-values for each state–action pair and pass those values into the same SPMD update.

One useful connection: **tabular representation is a special case of linear representation.** Give each GridWorld state–action pair its own one-hot feature—a vector of length 32—and the weights are exactly the 32 Q-table entries. Fewer or shared features produce a genuinely different approximation.

My recommendation is to **implement tabular TD first, check the linear implementation using one-hot features, then try a smaller feature set**. Assuming the feedback concerns your TD enhancements, that is likely what “implement in tabular and linear” is asking for.
